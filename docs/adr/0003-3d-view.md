# ADR-0003: Interactive 3D view

**Status:** Accepted
**Date:** 2026-10-13
**Deciders:** The Progress Quest

## Context

Phase 3B adds a 3D view of the room. It must use the same geometry, measurements, furniture
positions and features as the 2D plan, and must not introduce a second room model. The 2D editor
remains the single source of truth: the 3D view is (for now) view-only, apart from selecting
furniture, and it updates whenever the project changes.

## Decision

### One model, two renderers, via a pure scene adapter

```
Project (src/model, the only source of truth)
   │  buildRoomModel(room, features, stairs)   buildFurniture(furniture)
   │        ← pure TypeScript, no WebGL, unit-tested
   ▼
RoomModel: floor polygon + stairwell holes, walls (footprint + door/window holes),
           opening parts, stair steps, fixtures        SceneFurniture[]: parts per piece
   │  RoomViewer.setRoom(…) / setFurniture(…)    ← Three.js, lazily loaded
   ▼
WebGL scene
```

- **`src/scene3d/model.ts`** is the geometry adapter. Every dimension it uses comes from the
  existing model functions:
  - `outlinePolygon` for the floor;
  - `wallBodies` for each wall's mitered footprint, plus `openingSpan`-style offsets for its
    door and window holes;
  - `featureFrame` / `doorLeaves` for doors;
  - `layoutStair` / `stairToRoom` for stairs;
  - `furniturePolygon` conventions for furniture.

  Because it's pure data, accuracy is tested without a GPU.
- **`src/scene3d/furnitureParts.ts`** turns each piece into a few boxes (tabletop and legs, seat
  and back, …) chosen by its kind. Every part stays inside the piece's real width × depth ×
  height box, so the 3D furniture never occupies more floor than the 2D plan shows.
- **`src/scene3d/three/`** holds all Three.js code. It is reached only through a dynamic
  `import()`, so it isn't part of the initial 2D download.

### Coordinates

The plan uses centimetres, with x to the right and y down the page. Three.js uses **metres**, with
y up. The conversion lives in one place (`toScene`):

```
three.x = plan.x / 100        three.z = plan.y / 100        three.y = height / 100
```

A top-down camera with "up" set to −z shows the plan exactly as drawn (not mirrored).

### What is drawn

| Element | Source | 3D form |
| --- | --- | --- |
| Floor | room outline (any simple polygon) | Flat shape with the same outline. "Down" staircases cut holes in it. |
| Walls | `wallBodies` (thickness, miters) | One solid per wall, from the floor to the ceiling height, with each face triangulated as a single polygon with holes (`wallFaces.ts`). Doors are notches, windows are holes, and openings reaching floor and ceiling split the wall. One piece per face means no seams where a wall meets the part above an opening. |
| Openings | door height; window sill and height | Real holes through the wall, with reveal faces inside them |
| Doors | width, hinge, swing, type | Frame plus leaves (hinged leaves shown ajar on their swing side; sliding panels in the wall plane) |
| Windows | width, height, sill height | Frame plus translucent glass |
| Stairs | sections, steps, rise, direction | One block per tread at its rise height, plus landings. "Down" stairs descend through the floor. |
| Furniture | kind, size, colour, rotation | Procedural parts inside the real bounding box. Unknown kinds become a box. |
| Rugs | size, colour | Thin slabs on the floor |
| Other features | existing sizes and elevations | Simple blocks or discs (outlets, switches, vents, radiators, columns, lights) |

### Data model changes (schema v5, backward compatible)

- **`room.wallColor`** (optional, default warm white). Older files simply don't have it.
- **Ceiling height** already exists as `room.height`, and changing it never alters 2D
  dimensions.
- **Door and window heights and sill heights** already exist. Zero or missing values fall back to
  205 cm (doors) and 120 cm (windows).
- **3D display preferences** are device preferences, not project data, the same as the theme:
  wall mode (all walls or dollhouse), shadows, and whether the navigation hint has been seen.

### Rendering choices

- **Rendering on demand:** the scene is drawn only when the camera moves, the window resizes or
  the project changes. There is no continuous loop, and orbit damping (inertia) is off.
- **Few draw calls:**
  - all furniture parts in one `InstancedMesh` (per-instance colour);
  - all stair blocks in one `InstancedMesh`;
  - walls one mesh per wall, so they can be hidden individually in dollhouse mode.
- **Cheap rebuilds:** the room (walls, floor, stairs, fixtures) and the furniture are built
  separately. Moving or recolouring a piece rebuilds only the furniture's instanced mesh, not
  walls, floor textures or materials. Unit shapes are shared, and replaced objects are disposed
  straight away.
- **Dollhouse view:** outer walls whose outward side faces the camera are hidden as the camera
  moves. This is purely visual; the model is untouched.
- **Lighting:** hemisphere light plus one directional light. Soft shadows are on by default for
  fine pointers and off for touch devices.
- **Resolution:** pixel ratio capped at 2, and the drawing buffer capped at about 4 megapixels.
- **Reliability:**
  - If WebGL is unavailable, or the context is lost, a message appears with a way back to the 2D
    plan.
  - On leaving 3D: everything is disposed and the context released, and all listeners and
    animation frames are removed.
- **Selection:** clicking or tapping furniture uses a raycast against the instanced mesh. The
  instance index maps to the furniture id, and the result goes into the app's shared selection,
  so 2D and 3D always agree. There are never duplicate records.

### Diagnostics

While the 3D view is open, `window.__roomination3D` (typed in `src/scene3d/diagnostics.ts`)
exposes:
- render statistics;
- screen positions of plan points and furniture;
- the number of visible walls;
- the camera position.

Browser tests and the performance test use it to check accuracy (for example, the top-down view
keeps the plan's proportions to within 1%) without comparing pixels. It reads local state only.

### Measured (stress project: 40 walls, 150 pieces, 4 doors, 5 windows, 3 staircases)

| | Apple M3 Pro, Metal | SwiftShader (CI, software) |
| --- | --- | --- |
| First frame after switching to 3D (production build) | 0.26 s | 2.3 s |
| Scene build | 7 ms | 8 ms |
| Orbit frame rate | 60 fps (display limit) | 35 fps |
| Draw calls / triangles | 53 / 16,772 | 53 / 16,772 |

Three.js adds 154 KB (gzipped) in a separate file, downloaded only when 3D is first opened. The
main bundle grew by about 1 KB.

## Options considered

- **A separate 3D model in the project file:** rejected. It would drift from the 2D plan.
- **A 3D engine with built-in editing** (e.g. Babylon.js, a full editor): larger, and this phase is
  view-only.
- **Three.js, lazily loaded, with a pure adapter: chosen.** Three.js is MIT-licensed, has no
  runtime CDN, and Vite code-splits it.

## Consequences

- **Easier:** 3D can never contradict 2D, and accuracy tests run without a GPU. A later 3D
  editing phase can write through the same reducer actions.
- **Harder:** furniture looks are deliberately simple (boxes arranged per kind).
- **Not covered:** multi-storey buildings, ceilings with different heights, and per-wall colours.
